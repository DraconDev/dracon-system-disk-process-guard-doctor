  The tier model I'd build around

  Your instinct for a distinction is right, but I'd make it four tiers, not
  three — the "hold for now" tier is the one that prevents both hoarding and
  regret:

  • Hot (nvme, working): sources, active target/, daily builds. Never moved,
    never symlinked away — nvme speed matters here.
  • Warm / quarantine (second disk, TTL'd): "keeping for now, will probably
    delete." Explicit expiry (e.g. 30 days), then auto-delete. This is neither
    trash nor archive — it's the missing concept.
  • Cold (second disk, symlinked): big, rarely touched, genuinely kept — media,
    datasets, old checkouts, archives. Moved once, reached via managed symlink.
  • Trash (delete): aged-out quarantine, stale build outputs, node_modules,
    caches — what guard clean already handles.

  Rules of thumb: symlink cold directories, never individual files; never
  relocate target/ (rebuild instead — cheaper than cross-disk I/O); never
  auto-delete anything without a quarantine stop first.

  Second disk plan (Phase 0 — manual, today, no code)

  1. Verify the old home is fully migrated (/mnt/extra-drive-check/home/dracon),
     then delete it, the duplicate swapfile~/swap.img, and old timeshift
     snapshots. That alone may free ~150G+.
  2. Give it a stable identity: rename the mount to /mnt/data (UUID-based fstab
     entry; "extra-drive-check" is a provisional name and everything will key
     off this path).
  3. Layout: /mnt/data/cold/, /mnt/data/quarantine/.
  4. Manually move 2–3 biggest cold dirs (I'll name them once the home scan
     lands) and leave symlinks. This un-fires / immediately.

  Inner-system features (Phase 1–2 — the real build)

  In priority order, all building on existing code:

  1. Multi-mount guard. Guard currently watches one mount (disk_mount_path). It
     needs per-mount state: / at 97% is critical while /mnt/data at 60% is fine,
     and actions must target the pressured mount.
  2. relocate command on top of link policy.
     dracon-system relocate <path> --to cold = verified copy → swap in symlink →
     policy entry → link doctor confirms. Reversible by construction.
  3. Quarantine with TTL. guard clean moves ambiguous candidates to quarantine
     with a manifest (origin, date, size) instead of deleting;
     quarantine list/restore/expunge; guard auto-expires entries past TTL. This
     is your "hold then delete" made explicit.
  4. Cold-candidate suggestions at action level. When / hits action/critical,
     guard should propose (then optionally auto-apply) top cold relocations, not
     just deletions. Deleting a 6G target/ that rebuilds tomorrow is thrash;
     moving 50G of cold media is relief.

  Buckets (deferred — agree with you)

  Google's 5T is sensible only as a Phase 3 export for proven-cold data:

  tested restore path. Not first because: upload bandwidth, no shared lock with
  anything, credential-in-cloud risk, and it doesn't fix the actual problem (no
  tiering discipline — you'd just fill 5T the same way). Get the inner system
  right and cloud becomes a trivial overflow valve later.

  shaped for it. Manual relocate/quarantine are the actuators; the guard becomes
  the brain. Here's the design:

  Automatic tiering (proposed Phase 2 behavior)

  At action/critical, instead of going straight to deletion, the guard would:

  1. Relocate first, delete last. Scan relocate_candidate_roots (e.g. ~/Dev) for
     dirs that are: above relocate_min_size_gb, untouched for
     relocate_min_age_days, ignored-or-untracked by git, and not a build dir (
     target/, node_modules never qualify). Move them to relocate_cold_root until
     pressure drops below action — only then fall back to today's delete-based
     cleanup.
  2. Quarantine, don't delete, the ambiguous. guard clean moves gray-area
     candidates to quarantine with a manifest instead of deleting; expire reaps
     past-TTL on cadence. Nothing vanishes without a 30-day undo window.
  3. Refuse to fight live producers. The 79G-growth case we're watching right
     now is the rule, not the exception: a candidate modified within the guard
     interval is skipped (same philosophy as the cargo/rustc build protection).
     Fresh /tmp churn stays producer-side, but the guard would fingerprint it
     ("37 copies, ~48G, one per 8 min") and notify with the culprit pattern
     instead of silently losing.

  Safety rails (non-negotiable for auto-move)

  • Report-only default, matching the codebase's observation-first posture: new
    auto_relocate_apply = false must be explicitly flipped, exactly like
    auto_cleanup_apply today.
  • No --allow-tracked in auto mode, ever. Tracked dirs are invisible to the
    scanner.
  • Verify-then-cutover is already in relocate (count+bytes match or the source
    stays) — auto mode inherits it.
  • Daemon-owned state, human-owned policy. Auto-relocations get recorded in a
    daemon state file (e.g. relocations.json) that link doctor also reads,
    rather than the daemon editing your TOML and clobbering hand-written
    entries.
  • Broken-link alerting: link doctor runs inside the daemon loop; a dangling
    cold link notifies rather than silently rotting.
